# פתרון ניסוי ביצועים

## פתרון ראשון

הקצב מחלק את מספר החיפושים בזמן של אצווה שלמה. הוא אינו מודד את האחוזון של חיפוש בודד ואינו כולל בניית מפות ושאילתות. נציג את שלושת הגדלים כשלושה תנאי ניסוי ונבדוק אם היחס בין הגרסאות משתנה עם גודל המאגר.

## פתרון שני

נחליף את הפקת המפתח בשימוש בטווח כפול, ונחליף בכל פונקציית חיפוש את ההנחה שהמפתח קיים בערך ברירת מחדל מוסכם. הקטעים הבאים הם החלפות בתוך התוכנית המלאה.

```rust
state % (2 * size)
```

```rust
sum.wrapping_add(map.get(black_box(key)).copied().unwrap_or(0))
```

הגבול המקורי על גודל המאגר מונע גלישה בכפל הזה. מספרים בטווח העליון אינם נמצאים במפות, ולכן בדפוס אחיד צפוי שחלק ניכר מהחיפושים ייכשלו במציאה. אם נדרשת בדיוק מחצית, ניצור רצף זוגות שבו אחד קיים ואחד חסר ואז נערבב לפי זרע מתועד. חיפוש חסר יכול לעבור מסלול שונה ולכן משנה את העומס הנמדד.

## פתרון שלישי

נגדיר מראש תמהיל בקשות וקצב הגעה מוצע, ונרשום זמן כניסה, זמן התחלת טיפול, זמן סיום ותוצאה. נציג אחוזונים לכל קבוצת גודל יחד עם מספר כישלונות וחריגות זמן, בלי למחוק את הבקשות האיטיות מהסיכום. בנוסף נמדוד זמן מעבד וזיכרון תחת אותה מכסה.

שינוי שמגדיל אצוות יכול להעלות קצב כולל ולהרע לבקשות קטנות שהגיעו מאוחר. שינוי ששומר יותר נתונים במטמון יכול להאיץ בדיקה מקומית אך ליצור לחץ זיכרון במכונה המשותפת. הדוח צריך להציג את העסקה הזאת ולא להסתפק במדד הכולל הטוב ביותר.
